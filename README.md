# UtilityPaymentJournal (Журнал учета коммунальных платежей и жалоб ЖКХ)

Современное высокопроизводительное веб-приложение для ведения показаний приборов учета (воды, электроэнергии), управления жилыми объектами, поставщиками услуг, а также ведения жалоб на коммунальные услуги с использованием интерактивной Канбан-доски.

Проект спроектирован по канонам **чистой архитектуры (Clean Architecture)** с применением **вертикальных срезов (Vertical Slice Architecture)** и паттерна **CQRS**. Безопасность и производительность оптимизированы под высокие промышленные стандарты.

---

## 🛠 Технологический стек и инфраструктура

* **Бэкенд-платформа:** .NET 8.0 / ASP.NET Core (Гибридная архитектура:  MVC Controllers & Views + REST API)
* **База данных:** PostgreSQL + Entity Framework Core 8
* **Архитектурные паттерны:** Vertical Slice Architecture, CQRS (MediatR), Pipeline Behaviours
* **Использование современных фич C#:** Применение неизменяемых записей (`record`) для команд CQRS и вложенных DTO (Nested Records). Активное использование **первичных конструкторов (Primary Constructors)** для лаконичного внедрения зависимостей в контроллеры и хэндлеры, а также выражений паттерн-матчинга (**Switch Expressions**) для прозрачной трансформации статусов доменной логики в REST-ответы API (AccountApiController).
* **Валидация данных:** FluentValidation (Асинхронный валидационный барьер на базе `Task.WhenAll`)
* **Логирование и мониторинг:** Serilog + Сквозной сбор логов Kestrel -> Сервер логов **Seq**
* **Интеграционное тестирование (100% покрытие ключевых сценариев):** xUnit, Microsoft.AspNetCore.Mvc.Testing (WebApplicationFactory), Testcontainers.PostgreSql, Respawn (Respawner), FluentAssertions
* **Избирательное Unit-тестирование:** xUnit, NSubstitute, FluentAssertions
* **Безопасность:** ASP.NET Core Identity (Аутентификация на основе cookie-файлов), Строгая CSRF/Antiforgery защита
 **Фронтенд-оркестрация:** JavaScript (Нативный HTML5 Drag and Drop API), jQuery (Двухшаговые AJAX-запросы), Bootstrap 5 (Модальные окна, компоненты & Icons), Автоматический перевод UTC-дат в местное время пользователя
* **Окружение и Контейнеризация:** Docker, Docker Compose, Конфигурация через шаблон переменных окружения `.env.example` (настроен для запуска «из коробки»)

## 🏗 Архитектурные особенности проекта

### 1. Вертикальные срезы (Vertical Slice Architecture)
Вместо классического разделения на слои `Controllers / Services / Models`, проект структурирован вокруг **бизнес-фич** в папке `Features`. Каждый вертикальный срез полностью автономен и содержит собственные контроллеры, команды (`Commands`), запросы (`Queries`), хэндлеры (`Handlers`), DTO и валидаторы. 

Внутри `Features` реализованы модули:
* **`Account`**: Управление сессиями пользователей (Вход / Выход / Контроль доступа).
* **`Users`**: Управление пользователями и их системными ролями.
* **`ComplaintBoard`**: Интерактивная Канбан-доска жалоб с возможностью создания, удаления, изменения и перетаскивания (с изменения статуса карточки).
* **`ElectricityReadings` & `WaterReadings`**: Изолированный учет и валидация показаний счетчиков электроэнергии и воды.
* **`Residences`**: Управление списком жилых объектов текущего пользователя.
* **`Utilities`**: Каталог услуг с реализацией паттерна мягкого удаления (**Soft Delete** через флаг `IsActive`).
* **`UtilityProviders`**: Справочник поставщиков коммунальных услуг.

### 2. Сквозной валидационный барьер (Validation Pipeline)
Входные данные проверяются автоматически до того, как запрос попадет в бизнес-логику. С помощью открытых типов поведений MediatR (`IPipelineBehavior`) реализован класс `ValidationBehavior`. Он находит все связанные правила `FluentValidation`, запускает их **параллельно** через `Task.WhenAll` и в случае ошибок выбрасывает исключение, которое трансформируется глобальным фильтром в красивый REST-ответ `400 Bad Request`.

### 3. Оптимизация СУБД и уничтожение проблемы N+1
В модуле управления пользователями стандартный `UserManager` от Microsoft заменен на оптимизированный сервис `UserQueryService`. Проблема N+1 запросов при выгрузке ролей и проблема Декартова произведения решены на уровне СУБД с помощью эффективных ручных `LEFT JOIN` и обязательной группировки `.GroupBy()` прямо на стороне PostgreSQL. Весь массив данных выгружается за **один сетевой запрос** с агрессивным использованием `.AsNoTracking()` для экономии памяти на Change Tracker.

### 4. Нулевые аллокации при логировании (Source Generators)
Логирование этапов выполнения команд написано с использованием передовых генераторов исходного кода (`[LoggerMessageAttribute]`). Строки логов компилируются на этапе сборки проекта, полностью исключая упаковку типов (Boxing) и аллокацию памяти под массивы аргументов на лету. Все структурированные логи отправляются в Serilog, откуда автоматически пересылаются на сервер централизованного мониторинга **Seq**.

### 5. Сквозной UTC-конвейер работы с датами (End-to-End UTC)
Для исключения коварных сдвигов времени и часовых поясов внедрен жесткий пайплайн дат:
* **Отправка на бэкенд (`toUtcIsoString`):** При создании или изменении жалобы JavaScript считывает местное время на компьютере пользователя, автоматически переводит его в UTC и отправляет на сервер. База данных (PostgreSQL) получает «чистое» время.
* **Получение с бэкенда в форму (`formatForDateTimeLocal`):** При открытии модального окна редактирования система берет UTC-дату с сервера, сдвигает её обратно на локальный часовой пояс пользователя и приводит к виду `YYYY-MM-DDTHH:mm`. Это позволяет стандартным полям ввода корректно отображать местное время.
* **СУБД**: Флаг `Npgsql.EnableLegacyTimestampBehavior = false` принудительно заставляет EF Core помечать данные из колонок `timestamptz` как `DateTimeKind.Utc`, гарантируя стабильность времени на проде.

### 6. Прагматичная стратегия тестирования (Integration & Targeted Unit Testing)
Ввиду использования архитектуры вертикальных срезов, упор сделан на сквозную надежность системы при сохранении высокой скорости разработки:
* **Интеграционное тестирование (Основной контур)**: Покрывает приложение сквозными сценариями с помощью **WebApplicationFactory**. Тесты проверяют полную цепочку: от HTTP-запроса (REST API / Razor Pages), прохождения сквозного `ValidationPipeline` и кастомных конвертеров до реального выполнения SQL-запросов в СУБД. Это гарантирует, что все компоненты системы корректно интегрированы друг с другом.
* **Избирательное Unit-тестирование**: Применяется изолированно для наиболее критичных вертикальных срезов, содержащих сложную доменную логику. Зависимости в таких изолированных сценариях мокируются, а проверки пишутся с использованием **FluentAssertions**.

## ⛓ Фронтенд-оркестрация и паттерн CQRS Read-Side Refresh (на примере Kanban-доски)

В проекте используется продвинутый UX-паттерн оптимистичного обновления интерфейса и двухшаговой синхронизации данных через AJAX без полной перезагрузки страницы:

1. **Оптимистичный UI:** При перетаскивании карточки жалобы в другую колонку JavaScript мгновенно перемещает элемент в DOM-дереве (`column.appendChild(card)`). Пользователь видит мгновенный отклик интерфейса, не дожидаясь ответа от сервера.
2. **Шаг 1. Вызов Команды (Запись):** Фронтенд извлекает CSRF-токен из разметки и отправляет легковесный асинхронный **`PATCH`**-запрос на API-эндпоинт `/api/complaint-board/{id}/change-status`, передавая токен безопасности в заголовке `RequestVerificationToken`. Эта операция атомарна, она не делает тяжелых связанных `Include` в СУБД и выполняется бэкендом сверхбыстро.
3. **Шаг 2. Вызов Запроса (Чтение):** При успешном изменении статуса (`success`) JavaScript-оркестратор автоматически выполняет второй точечный **`GET`**-запрос к Query-сервису бэкенда (`/api/complaint-board/{id}`) для получения актуальной развернутой модели данных. 
4. **Реанимация DOM (buildCardHtml):** Полученные JSON-данные передаются в функцию `buildCardHtml(fullData)`, которая на лету генерирует свежую HTML-разметку и бесшовно замещает старую карточку через `.replaceWith()`. Это позволяет мгновенно отобразить новые вычисляемые сервером поля (например, появление *«Даты решения»* при переносе карточки в колонку «Решенные») и обновить общие счетчики задач (`updateCounters()`).
5. **Стратегия безопасного отката (Rollback):** В случае сетевого сбоя или отказа валидации на стороне СУБД, система перехватывает ошибку, выводит уведомление (`tryShowServerError`) и выполняет принудительный сброс состояния интерфейса через `location.reload()`, возвращая карточку на её исходное место.

> 💡 **Интеграционное покрытие:** Данный сквозной UI/UX-пайплайн полностью воспроизводится в интеграционных тестах через `WebApplicationFactory`. Тестовый клиент имитирует отправку фоновых `PATCH`-команд с валидными `Antiforgery`-токенами, проверяет корректность статус-кодов, а затем симулирует последовательный `GET`-запрос к Query-сервису для верификации консистентности данных.

## 🔒 Безопасность и интеграция со Swagger UI

Приложение спроектировано по принципу **Secure by Default** через глобальную политику `FallbackPolicy` (все эндпоинты защищены по умолчанию, анонимный доступ выдается точечно через `.AllowAnonymous()`). 

Обеспечена одновременная работа Cookie-авторизации и защиты от CSRF-атак как для страниц приложения, так и для **Swagger UI**:
* Создан `SwaggerAntiforgeryFilter` (`IOperationFilter`), который строго через типы `typeof()` (без хрупких строк) сканирует контроллеры на наличие защиты и автоматически выводит поле ввода заголовка безопасности.
* Имя заголовка централизовано в константе `AntiforgerySecurityConstants.AntiforgeryHeaderName` ("RequestVerificationToken"), связывая воедино jQuery AJAX-запросы страниц и песочницу Swagger.
* Перехвачены события `OnRedirectToLogin` на бэкенде: если неавторизованный запрос прилетает от API или Swagger, сервер возвращает честный REST-статус `401 Unauthorized` / `403 Forbidden` вместо неуместного редиректа `302 Found`.

📦 Контейнеризация и Сценарии Запуска

Инфраструктура приложения полностью оркеструется через `docker-compose.yml` и разделена на **3 изолированных контейнера** с настроенным контролем последовательности запуска через механизмы Docker Healthchecks:
1. **`postgres`** — Реляционная база данных PostgreSQL 17+. Оснащена встроенной проверкой готовности (`pg_isready`), гарантирующей, что СУБД полностью поднялась и готова принимать соединения.
2. **`seq`** — Сервер централизованного сбора и индексации структурированных JSON-логов от Serilog.
3. **`webapi`** — Контейнер приложения ASP.NET Core. Благодаря директиве `depends_on: postgres: condition: service_healthy`, приложение стартует строго после полной готовности СУБД. При запуске бэкенд автоматически и безопасно накатывает миграции EF Core на чистую базу данных.

### Сценарий 1. Быстрый запуск через консоль (Кроссплатформенный CLI)

Для работы контейнеров нужен файл `.env`. Если вас устраивают стандартные порты и настройки из шаблона, вы можете скопировать его и запустить проект одной командой. 

*Если стандартные порты заняты вашими локальными сервисами, сначала скопируйте `.env.example` в `.env`, откройте его и отредактируйте настройки вручную перед запуском.*

Выполните команду в корневой папке проекта в зависимости от вашей ОС:

* **В Windows (PowerShell):** Скопировать шаблон и сразу поднять контейнеры:
  ```powershell
  cp .env.example .env; docker compose up --build
  ```

* **В Linux / macOS / Git Bash:**
  ```bash
  cp .env.example .env && docker compose up --build
  ```
*Флаг `--build` принудительно перекомпилирует исходный код внутри Docker-образа, гарантируя запуск самой актуальной версии бэкенда.*

### 🧪 Изоляция и стратегия тестового контура

Тестовый контур спроектирован с упором на максимальную надежность и изоляцию от рабочей среды. В проекте используется двухуровневая стратегия верификации кода:

#### 1. Сквозное интеграционное тестирование (100% покрытие ключевых сценариев)
Основной щит приложения — полные интеграционные тесты на базе кастомной фабрики **`IntegrationTestWebAppFactory`**. Они автоматически разворачивают изолированное окружение в Docker без необходимости ручной настройки:
* **Контейнеризация (Testcontainers):** При старте сессии фабрика поднимает эфемерный контейнер реальной СУБД `postgres:16-alpine`. Это гарантирует, что тесты проверяют настоящий сырой SQL-код и особенности поведения EF Core 8 в PostgreSQL, а не их легковесные заменители в памяти.
* **Изолированный накат миграций:** Структура БД разворачивается путем автоматического наката миграций EF Core до запуска самого веб-сервера Kestrel, что исключает состояние гонки (race conditions).
* **Сверхбыстрый сброс состояния (Respawner):** База данных не пересоздается для каждого теста. Утилита **Respawner** от Jimmy Bogard за миллисекунды очищает таблицы схемы `public` между тестами, обеспечивая абсолютную независимость каждого прогона.
* **Тестовая аутентификация:** Фабрика инкапсулирует схему `TestAuth` и предоставляет преднастроенный `HttpClient`, позволяя имитировать запросы от лиц пользователей с любыми ролями в обход реальной формы входа.

#### 2. Избирательное Unit-тестирование (Таргетированный контроль бизнес-логики)
Юнит-тесты применяются **строго избирательно** — только для наиболее критичных вертикальных срезов, содержащих сложную доменную логику, ролевые барьеры или ручное управление транзакциями. 
* Пакет **NSubstitute** используется для создания изолированных заглушек (моков) таких системных компонентов, как `UserManager`, `RoleManager` и контекстов транзакций.
* Пакет **FluentAssertions** обеспечивает жесткий контроль логики — например, гарантирует, что при создании пользователя транзакция закроется методом `.CommitAsync()`, а в случае сбоя гарантированно вызовется `.RollbackAsync()`.
